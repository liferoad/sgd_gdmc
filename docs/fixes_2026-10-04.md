# Fixes applied - 2026-10-04

This document records the changes made in response to
[review_2026-10-04.md](review_2026-10-04.md). Every defect listed in that
review has either been fixed in code or explicitly scoped out, and the two
headline experiments were re-run.

## Revision 2 - follow-up review findings

A second review of the patch found five further issues. All five are fixed,
and the experiments affected by them were re-run (the numbers in section 6 are
from the re-run):

1. **Separate acceptance compared losses from two different batches.** With
   accept_on="separate", loss_old came from the gradient batch and loss_new
   from the acceptance batch, so the batch offset entered the Metropolis
   decision. step() now evaluates the accept closure *before* the proposal and
   uses those two values as the Metropolis pair. A regression test rejects a
   move that lowers the acceptance loss from 101 to 100.111 while the gradient
   batch sits at 1.
2. **De-duplication ran before the JSON settings were expanded**, so runs that
   differed only in gradient-noise level collapsed: Adam's 15 noise-study rows
   became 3. The aggregator now expands the extra column first and de-duplicates
   only runs identical in every other setting.
3. **The aggregation key omitted beta, lr, momentum, move_frac,
   project_lr_scale, epochs, batch_size and select_mode**, so the beta=0
   (always-accept) and beta=2 rows were pooled into one count=6 cell and lr
   sweeps were merged. The key is now the complete configuration and count is
   the number of distinct seeds.
4. **The in-place snap ignored per-tensor ranges.** UniformGrid(per_tensor=True)
   had no range_for, so the snap used the raw vmin/vmax multipliers as absolute
   bounds and could rescale already-quantized weights. UniformGrid now exposes
   the same range_for / snap_with_range / step_with_range API as AdaptiveGrid,
   the range is captured once from the full tensor, and the snap stays in place.
5. **Memory accounting was inconsistent**: Adam reported only its moments while
   GDMC was credited with 4/8 bytes per parameter that included gradients.
   Optimizer state is now measured uniformly from the state dict (Adam 8.0,
   8-bit Adam 2.0, GDMC v1 0.0, GDMC v2 4.0 B/param) with gradients reported
   separately.

Also fixed at the same time (they predate the patch):

* **Eval-mode restoration**: _eval left the model in eval() mode, silently
  disabling dropout for the rest of the epoch.
* **Dropout / BatchNorm acceptance state**: the acceptance forward passes
  re-sampled dropout and advanced BatchNorm running statistics, so rejected
  moves still mutated the model. The training loop now passes an eval-mode
  accept closure that snapshots and restores every BatchNorm buffer and the
  training mode.

## Revision 3 - second follow-up review

Four further issues, all fixed, plus the low-bit experiment the review asked
for.

1. **The adaptive grid was recomputed between the snap and the proposal.**
   AdaptiveGrid derives its range from the current weights, so snapping
   changed the weights and the proposal then used a *different* grid;
   rollback restored re-snapped values rather than the actual pre-proposal
   weights, so even a rejected move changed the model. step() now captures
   the range once per parameter and uses it for the snap, the proposal and
   the rollback, and the rollback target is the exact value at each moved
   index. Regression test reproduces the reported case: with
   AdaptiveGrid(alpha=1.05), a forced rejection restores
   [-0.6615, -0.2205, 0.2205, 0.6615] exactly, while the old code would have
   re-snapped them on the range derived from those same values.
2. **Confidence intervals were computed over rows, not seeds.** count used
   unique seeds but mean/std/CI used every row, so a configuration recorded
   in two CSVs (the historical MNIST CNN 4-bit GDMC config has six rows from
   three seeds) got an interval that was about 2.6x too narrow. Statistics
   are now computed over one value per (configuration, seed); disagreeing
   duplicates are averaged and counted in a new conflicts column, so they are
   visible instead of being treated as independent repetitions.
3. **The comparison plots still pooled configurations.** plot_loss_curves and
   plot_acceptance averaged every row for an (optimizer, grid) pair, so the
   noise figure mixed noise strengths, acceptance modes and beta values, and
   the corrected-baseline figures mixed learning rates. Every plotted line now
   fixes all settings except one axis; when bits do not vary, a second figure
   is emitted against the varying axis (noise strength, learning rate, ...)
   and stale figures are removed rather than left behind.
4. **The movement test could pass because of the initial snap.** It compared
   final weights against the unquantized initialization, so snapping alone
   could satisfy it (a 32-bit fixed-step run reported two moved coordinates
   with zero real change). Movement is now measured from the post-snap state,
   the 32-bit fixed-step no-op is tested as its own documented limitation, and
   the auto-k fix is tested separately. last_num_moved counts entries whose
   value actually changed and last_accepted_step_size is the actual mean
   displacement, not the nominal k * delta.

The review also noted that the corrected comparison contained only momentum
GDMC, and that 8-bit Adam compresses optimizer state but keeps FP32 weights so
it is not a same-precision comparator. experiments/15_lowbit_comparison.py
addresses both: basic GDMC (beta1=0, k=1), momentum GDMC, projected Adam,
projected momentum SGD and a latent-weight QAT/straight-through baseline, all
on the same grid at 2/4/8 bits with a matched validation-based tuning budget,
plus FP32 Adam as the accuracy reference, reported per seed so paired
differences are possible.

## 2. Metropolis acceptance: observable and configurable

The review found that acceptance was inert (median accepted fraction 1.0000)
in every reported MNIST run, that accept_on was documented but never read, and
that there was no way to hold out an acceptance batch. Now:

* Whenever an accept closure is supplied, it is evaluated BEFORE and AFTER the
  proposal and those two values are the Metropolis pair. Mixing batches cannot
  enter the decision.
* accept_on="separate" selects a different batch, supplied by
  TrainConfig.accept_split (in-batch hold-out) or TrainConfig.accept_loader
  (cycled held-out loader). accept_on="minibatch" keeps the same batch.
* The training loop always supplies the accept closure for GDMC, and it
  evaluates in eval() mode with BatchNorm buffers and the training mode
  restored afterwards - a deterministic, side-effect-free acceptance loss.
* accept_on="full", which never existed, now raises instead of being silently
  ignored.
* Per-run diagnostics: delta_loss, num_moved, accepted_step_size,
  mean_acceptance_rate, plus last_grad_loss for the gradient-batch loss.
* Calling step(closure) without an accept closure keeps the legacy behaviour
  (the gradient closure is re-used for the acceptance loss).

Note: the inertness itself is a research finding, not a bug. The fix makes it
measurable and lets the acceptance ablation (accept vs always-accept) run.

## 3. Memory: sparse proposals and bounded rollback

Before: every step materialised full-size snap, candidate and delta tensors per
parameter, a bool mask, and an int64 randperm, and kept all snapshots and deltas
alive until the Metropolis decision. After:

* proposals and rollback are stored sparsely - only the moved indices and their
  old/new values (O(move_frac * numel));
* the move set is drawn with rand < move_frac (select_mode="bernoulli", the
  default) instead of a full int64 permutation; select_mode="randperm" keeps
  the legacy behaviour;
* weights are snapped in place rather than via a full-size copy;
* the auto-k gradient reference uses a chunked abs-mean (no full-size abs temp).

Measured peak-RSS growth during the optimizer step (21M-parameter model, 3
steps, one method per subprocess; before = analysis/review/01_memory_probe.py,
after = experiments/13_memory_benchmark.py):

| optimizer | before (B/param) | after (B/param) | optimizer state (B/param) | gradients (B/param) |
|---|---:|---:|---:|---:|
| FP32 Adam | 26.3 | 22.3 | 8.0 | 4.0 |
| 8-bit Adam (new) | - | 8.8 | 2.0 | 4.0 |
| GDMC v1, move_frac=0.01 | 39.0 | 11.8 | 0.0 | 4.0 |
| GDMC v2, move_frac=0.01 | 43.7 | 15.5 | 4.0 | 4.0 |
| GDMC v2, move_frac=1.0 | 71.0 | 55.6 | 4.0 | 4.0 |

Optimizer state is measured from the state dict, so it excludes weights and
gradients (GDMC without momentum has no optimizer state at all). The measured
peak growth is a different metric and includes gradients, autograd temporaries
and the per-step proposal buffers. So GDMC v2's per-step peak went from 1.66x
FP32 Adam to about 0.7x, and 8-bit Adam - the honest comparator for a packed
low-bit GDMC - is now measured rather than assumed. Run-to-run variance on
these RSS numbers is roughly 10%.

Reproduce with:

    .venv/bin/python experiments/13_memory_benchmark.py

## 4. Reporting, statistics and reproducibility

* De-duplication of the replicated unquantized baselines now runs only after
  the JSON extra settings are expanded, and only merges runs identical in
  every other setting - noisy runs are never collapsed.
* The group key is the complete configuration (task, model, optimizer, grid,
  bits, epochs, batch size, lr, momentum, beta, move_frac, beta1, k, k_mode,
  step_scale, project_lr_scale, grad_noise_rho, accept_on, select_mode) and
  count is the number of distinct seeds.
* analysis/aggregate.py now groups on the *full* configuration (beta1, k,
  k_mode, step_scale, noise, acceptance) instead of pooling them, de-duplicates
  the unquantized baselines that were replicated across bits, and reports a 95%
  t-interval per cell. The previous table reported mnist_mlp_long_v2 as one row
  with count=9, mixing k=1 and k=4 runs; it is now six rows.
* results/REPORT.md is generated from the data rather than hard-coded literals.
* final_train_loss was NaN in 633/633 rows; the training loop now carries the
  last real training loss into the final record.
* Each run gets its own torch.Generator, handed to the optimizer, so optimizers
  no longer perturb the global RNG stream. Runs with the same seed now share a
  minibatch order (common random numbers), which the test suite asserts.
* RNG use is device-correct (a CPU generator is adapted to the tensor's device),
  verified with a GDMC step on MPS.
* Stale/corrected claims are flagged at the top of results/REPORT.md's source
  docs: docs/test_report.md and docs/review_2026-10-04.md.

* **The 4.3x low-bit win over Projected-GD was a baseline artifact.** Tuned

### Gradient-noise study (experiments/14, MNIST MLP, 8 epochs, full 60K, 3 seeds)

Noise eps = rho * RMS(g) * N(0,1) per tensor, added to the proposal gradient
only. Best test accuracy (mean over 3 seeds); raw data in
results/raw/noise_study.csv.

| method | rho=0 | rho=0.1 | rho=0.3 | rho=1 | rho=3 | change (3-0) |
|---|---:|---:|---:|---:|---:|---:|
| FP32 Adam | 0.9793 | 0.9781 | 0.9788 | 0.9782 | **0.9746** | **-0.0048** |
| GDMC v2, 8-bit, Metropolis | 0.9733 | 0.9741 | 0.9728 | 0.9687 | 0.9490 | -0.0243 |
| GDMC v2, 8-bit, always accept | 0.9733 | 0.9741 | 0.9728 | 0.9687 | 0.9490 | -0.0243 |
| GDMC v2, 4-bit, Metropolis | 0.9260 | 0.9285 | 0.9285 | 0.9146 | 0.8942 | -0.0318 |
| GDMC v2, 8-bit, separate acceptance | - | - | - | 0.9613 | 0.9396 | - |

95% CIs at rho=3: Adam [0.9720, 0.9771]; GDMC-8 [0.9479, 0.9502];
GDMC-4 [0.8869, 0.9015]; separate acceptance [0.9379, 0.9413]. Every GDMC
variant is below Adam (Welch p <= 1.2e-4).

What this says:

* **The noise-resilience hypothesis is not supported.** Adam loses 0.5 points
  at rho=3; GDMC-8 loses 2.4 and GDMC-4 loses 3.2 - a 5-7x larger degradation.
  Noise widens the existing gap rather than closing it.
* **The Metropolis step contributes exactly nothing, at any noise level.**
  The accept and always-accept columns are identical to four decimal places at
  every rho (p=1.0), and the reported acceptance rate stays 1.000 even at
  rho=3: with a 1% move-set and one grid step, Delta-L is below minibatch
  noise no matter how noisy the gradient is.
* **Separate acceptance is slightly worse, not better** (0.9396 vs 0.9490 at
  rho=3), so the same-batch optimism bias was not the problem. Its acceptance
  rate is 0.998-0.999 (the same-batch runs are at 1.000), confirming that the
  step is inert at these move sizes.

Caveats: one task and architecture, 8 epochs, 3 seeds, Gaussian noise only
(no outlier or sign-flip injection), and GDMC is quantized while Adam is not,
so part of the level gap is the quantization constraint rather than noise.
The degradation column is the noise-specific part.

### Same-precision low-bit comparison (experiments/15)

The powered version of this experiment covers MNIST (10 seeds) and
Fashion-MNIST (8 seeds) with the same uniform grid, the same three-candidate
validation-based tuning budget per method, and paired analysis. Full tables:
results/lowbit_summary.md and results/lowbit_paired.csv; the goal-by-goal
write-up is docs/research_goals.md.

Paired difference vs projected Adam, matched by seed (best of run / final):

| task | bits | GDMC v2 (best / final) | mean diff vs projected Adam | seeds favouring GDMC | paired p |
|---|---:|---|---:|---:|---:|
| MNIST | 4 | 0.9351 / 0.9335 | +0.0181 / +0.4429 | 10/10 | 0.001 |
| Fashion | 4 | 0.7925 / 0.7507 | +0.0397 / +0.1918 | 8/8 | 0.001 / 0.008 |
| MNIST | 8 | 0.9744 / 0.9743 | +0.0005 / +0.0036 | 5/10, 9/10 | 0.57 / 0.012 |
| Fashion | 8 | 0.8751 / 0.8751 | +0.0085 / +0.0117 | 8/8 | 0.0002 / 0.0006 |
| MNIST | 2 | 0.4945 / 0.4099 | -0.3015 / -0.0536 | 1/10, 4/10 | 0.0002 / 0.50 |
| Fashion | 2 | 0.3274 / 0.2923 | -0.4077 / -0.0666 | 0/8 | <0.001 / 0.23 |

* Basic GDMC (beta1=0, k=1) trains and is stable at every bit-width (MNIST
  final 0.777 / 0.892 / 0.943; Fashion 0.557 / 0.754 / 0.847) but is dominated
  by momentum GDMC everywhere and by projected Adam at 4-8 bits.
* Momentum GDMC beats projected Adam at 4 bits on both tasks, with every seed
  favouring it and paired p <= 0.001 on best-of-run accuracy.
* The final-accuracy gap is much larger because projected Adam peaks early and
  then collapses at low precision (MNIST 4-bit final 0.49 vs best 0.92). The
  advantage at 4 bits is best described as stability under aggressive weight
  quantization; best-of-run accuracy hides it.
* At 8 bits GDMC ties the baseline (within ~1 point), and at 2 bits it loses.
* Latent-weight QAT beats every direct-quantization method at 2-4 bits and
  matches FP32 Adam at 8 bits, so for extreme precision QAT remains the
  practical choice.

## 7. Still open

* **Packed persistent weights.** The memory work above bounds the proposal and
  rollback storage, but weights are still float32 with a float32 gradient. The
  feedback's 0.5 byte/parameter packed representation (no master-weight copy)
  is not implemented; the measured 8.4 B/param for 8-bit Adam is the number a
  packed GDMC would have to beat.
* **Re-running the historical sweeps (01-11).** Those CSVs predate the baseline
  fixes and are retained for provenance, but their baseline rows are not
  trustworthy; experiments 12 and 14 provide the corrected comparisons.
* **Outlier / sign-flip noise.** The noise study uses Gaussian noise only;
  occasional large outliers and explicit direction errors remain untested.
