# Project review and assessment of the "noise-resilient low-bit training" feedback

**Date:** 2026-10-04
**Status: the defects below have been fixed.** See
[docs/fixes_2026-10-04.md](fixes_2026-10-04.md) for the changes and the
post-fix measurements; this document is kept as the original review.

**Scope:** full read of `src/`, `experiments/`, `analysis/`, `docs/`, `results/raw/*.csv`;
plus four new scripts under `analysis/review/` (memory probe, Projected-GD
learning-rate sweep, gradient-noise pilot, headline verifier).
**Method:** every headline number below was recomputed from `results/raw/*.csv`;
nothing is taken from the write-ups on trust.

---

## TL;DR

**Project status.** `sgd_gdmc` is a well-documented, reproducible research
prototype (89 tracked files, 633 raw runs, per-step curves, an honest
`docs/future_work.md`). The v1 → v2 → v3 progression is real: v3 does
eliminate the 16/32-bit "plateau", and it replicates on Fashion-MNIST.
But the *headline scientific claims* are weaker than the docs state.
Three are artifacts of the evaluation setup rather than properties of
GDMC, and a fourth is a hypothesis the current code cannot test:

1. **Metropolis acceptance is inert in every reported MNIST MLP run.**
   Across all 48 per-step GDMC curves, the proposal acceptance fraction is
   median **1.0000**, min **0.9981**, mean **0.9997**. The "GDMC with
   Metropolis accept/reject" result is in fact "grid-snapped momentum
   sign-proposals with a stochastic 1 % move-set". The Monte-Carlo half of
   the method is untested by the current experiments.
2. **The Adam reference is under-tuned.** The long-run MLP baseline uses
   Adam at `lr=1e-2` and reaches 0.9757. The same model, same seeds, in
   the project's *own* v3 script at `lr=1e-3`, reaches **0.9832**. Every
   GDMC configuration in that seed-matched script is **below** Adam
   (Welch p ≤ 0.02). The headline "GDMC v2 8-bit matches/beats Adam
   (0.9775 vs 0.9757)" compares GDMC's best run to a mis-tuned baseline
   from a different script.
3. **The low-bit "QAT is broken" comparison is an untuned-baseline
   artifact.** `ProjectedGD` runs Adam at `lr=1e-2` then snaps. At 4 bits
   the grid spacing is 0.133, so the step is snapped back; it reaches
   0.20. With `lr=0.05` the *same* baseline reaches **0.83** at the same
   budget (probe 3). At 2 bits, tuned Projected-GD (**0.79**) actually
   *beats* GDMC v2 (0.70) at matched budget. The "GDMC is 4.3–6.9× better
   than QAT at 2–4 bits" claim rests on a frozen baseline.
4. **The noise-resilience thesis, tested directly, comes out negative.**
   In a controlled pilot (§3.3), FP32 Adam loses 0.6 points at ρ=3 while
   GDMC-8 loses 2.3; and turning Metropolis acceptance off changes nothing
   at any noise level (≤ 0.0007, p ≥ 0.38) because the acceptance signal is
   below minibatch noise.

**Feedback assessment.** The feedback is substantively correct and targets
exactly the right weak points. Its mechanism analysis is sound, its memory
arithmetic is right, and its two citations check out. Its two most
important claims — (a) resilience comes from mechanisms the project has
not ablated, and (b) the current implementation cannot demonstrate a
memory saving — are both confirmed here, and (b) is **understated**: the
current implementation uses *more* peak memory than Adam, not less
(measured 1.5–2.7×). Its blind spots: the memory table compares against
FP32 Adam when the right comparator is 8-bit Adam (against which packed
4-bit GDMC is ~15 % smaller, not 47 %); and its **central
noise-resilience hypothesis does not survive a first direct test**
(§3.3) — with norm-scaled Gaussian noise on the proposal gradient, FP32
Adam degrades 4× less than GDMC, and adding/removing Metropolis acceptance
changes nothing at any noise level.

### 1.4 Defects found (each with evidence)

**D1 — Metropolis acceptance never rejects on the headline tasks.**
Computed from the committed per-step curves:

```
results/curves/mnist_mlp_v3/*.csv, gdmc runs (n=48):
  median accepted fraction 1.0000, mean 0.9997, min 0.9981
  files with < 0.99 acceptance: 0 / 48
```

Across every task with committed curves (93 GDMC runs):

| task | runs | median accept | min | runs < 0.99 |
|---|---:|---:|---:|---:|
| MNIST MLP (v3) | 48 | 1.0000 | 0.9981 | 0 |
| Fashion-MNIST MLP | 45 | 0.9995 | 0.0006 | 13 |

On Fashion-MNIST, breaking it down by bits shows acceptance is inert at
≥4 bits (mean ≥ 0.99) and only engages at 2 bits (mean 0.79, min 0.001).
So in the regime the project claims as its win — 4–32 bits — the
Metropolis step accepts essentially everything.

The v2 toy sweep does show real rejection (acceptance 0.01–0.72 at 2–4
bits), and `docs/test_report.md §3.4` even notes "acceptance 1.0 does NOT
mean the model is improving". But the long-run write-ups still credit
"Metropolis accept/reject" for the 8-bit MNIST result
(`docs/long_runs.md §2`). It cannot: the acceptance step is a no-op there.

**D2 — Adam is under-tuned in exactly the runs that carry the headline.**
The Adam learning rate is inconsistent across scripts:
`1e-2` in `01/02/03/04` (short sweeps) and `07` (the long MNIST MLP/CNN
runs), but `1e-3` in `08/09/10/11`. Result (best test acc, same model and
seeds): `0.9757 ± 0.0012` at lr 1e-2 vs **`0.9832 ± 0.0009` at lr 1e-3**.
Momentum SGD at lr 1e-2 reaches 0.9808, i.e. a plain unquantized baseline
already beats the paper's headline GDMC number. In the seed-matched v3
script (Adam lr 1e-3) *every* GDMC configuration is below Adam, with
Welch p ≤ 0.02 (`04_verify_headlines.py` prints the full table).
`docs/test_report.md §2.5` states Adam uses 1e-3 for classification, which
is not true of the runs it describes.

**D3 — Projected-GD's low-bit failure is a step-size artifact.**
`ProjectedGD` = Adam(lr) → snap. At 4 bits δ=0.133; at 2 bits δ=0.667.
At the project-wide `lr=1e-2` the update is snapped back every step.
Probe 3 (MNIST MLP, 10K, 5 epochs, 3 seeds):

| bits | Projected-GD lr | mean best acc |
|---|---|---|
| 4 | 0.01 (as run) | 0.1997 |
| 4 | **0.05** | **0.8318** |
| 4 | 0.10 | 0.7012 |
| 4 | 0.20 | 0.1269 |
| 2 | 0.01 (as run) | 0.1987 |
| 2 | **0.30** | **0.7933** |
| 2 | GDMC v2 (same budget) | 0.7033 |
| 4 | GDMC v2 (same budget) | 0.9126 |

So the "QAT is broken at 2–4 bits" finding is a baseline-tuning artifact,
and at 2 bits a tuned QAT baseline beats GDMC.

**D4 — The memory claim is the opposite of the implementation.**
No packed storage exists anywhere: weights are float32 `p.data`, and each
step materialises full-size `snap` + `candidate` + `delta` (plus a bool
`mask` and an int64 `randperm`) per tensor. Probe 1 (21 M-param model,
peak RSS growth during `step`):

| method | bytes/param growth | persistent bytes/param (weights + grads + optimizer state) |
|---|---:|---:|
| Adam | 26.3 | 16.0 (4 + 4 + 8) |
| GDMC v1, move_frac=0.01 | 39.0 | 8.0 (4 + 4 + 0) |
| GDMC v2, move_frac=0.01 | **43.7 (1.66× Adam)** | 12.0 (4 + 4 + 4) |
| GDMC v1, move_frac=1.0 | 67.2 | 8.0 (4 + 4 + 0) |
| GDMC v2, move_frac=1.0 | **71.0 (2.70× Adam)** | 12.0 (4 + 4 + 4) |

(GDMC without momentum holds no optimizer state; the earlier wording of this
table conflated optimizer state with gradients. See
[fixes_2026-10-04.md](fixes_2026-10-04.md) for the corrected accounting and the
post-fix measurements.)

**D5 — Statistics and reporting.**
* Only mean ± std over 3 seeds; no confidence intervals, no per-cell
  significance tests anywhere.
* `analysis/aggregate.py` groups by `(task, model, optimizer, grid_spec,
  bits)` and **ignores `beta1`, `k`, `step_scale`** — so
  `mnist_mlp_long_v2` is reported as one pooled row (count=9) mixing
  `k=1` and `k=4` runs, and `gdmc_v3_auto_k` mixes `step_scale` values.
* `results/REPORT.md` hard-codes long-run numbers as literals, so the
  auto-generated report and the raw data can drift apart.
* `docs/test_report.md` says "Generated from `results/raw/*.csv` (327
  runs)"; the directory now holds **633** rows.
* `final_train_loss` is NaN in **633 / 633** rows (`records[-1]` is the
  synthetic final-eval record with `loss=nan`).
* **Seeds are not common random numbers.** `shuffle=True` draws its
  permutation from the global torch RNG, and `GDMCOptimizer._select_indices`
  also draws from that global RNG every step. Two optimizers run under the
  same `seed` therefore see *different minibatch orders* after the first
  step, so seed-matched differences include data-order noise. My noise
  pilot uses `shuffle=False` for this reason; fixing it properly means
  giving each run its own `torch.Generator` for both the sampler and the
  optimizer.

**D6 — Dead / misleading code and missing safety rails.**
* `accept_on` is documented as `{"minibatch","full"}` but is **never
  read**; only the same-minibatch path exists.
* The acceptance closure re-uses the *same* minibatch that produced the
  gradient (the bias `future_work.md` L6 already flags), and there is no
  hook to inject gradient noise — the feedback's central experiment needs
  new plumbing.
* All experiments hard-code CPU; `_select_indices` builds CPU index
  tensors, so a GPU port is not a one-liner.
* No unit tests, no CI, no assertion anywhere that the proposal actually
  changes the weights (which is how the 16/32-bit no-op survived to v3).

**D7 — Scale blockers (relevant to the large-model goal).**
Per optimizer step and per tensor, the current code allocates a full
`torch.randperm(numel)` (int64, 8 B/param) even though `move_frac=1 %`;
a bool mask (1 B/param); a `snapped` clone and a `candidate` clone (4 B
each); and it keeps all snapshots + deltas live for the whole step. For a
7 B-parameter model this is tens of GB of transient state per step, before
activations. "Train a larger model under a fixed memory budget" is not
reachable from this code path.

## 2. Assessment of the feedback

### 2.1 What is correct

| Feedback point | Assessment |
|---|---|
| Sign moves are invariant to positive gradient rescaling but vulnerable to sign-flipping noise | ✅ correct for v1/v2 (`-sign(g)`, `-sign(m_t)`) |
| Acceptance can filter harmful proposals, but only if the loss comparison is reliable; the same noisy minibatch weakens it | ✅ correct, and the project's own data is a direct demonstration: acceptance is inert (D1) |
| Memory: FP32 Adam 16 B/param; packed 4-bit GDMC 8.5 B/param ≈ 47 % less, *not* 8× | ✅ arithmetic checks out (0.5+4+4 vs 4+4+8) |
| The current implementation cannot establish that saving (float weights, full snapshots/deltas) | ✅ correct, **and worse than stated**: measured peak is 1.5–2.7× Adam (D4) |
| The noise-resilience hypothesis is untested; the four experiments do not exist | ✅ correct — there is no gradient-noise code path in `src/` at all |
| Evaluate acceptance on a separate train batch, not validation | ✅ correct; already identified internally as `future_work.md` Fix 6.1 |
| Need CIs and degradation *relative to each method's own noise-free result* | ✅ correct; nothing in the repo does this |
| 8-bit Adam and ECO are the right references | ✅ both citations verified (arXiv 2110.02861; arXiv 2601.22101, "ECO: Quantized Training without Full-Precision Master Weights") and correctly characterised |
| Final target: lower *measured* peak memory at Adam-comparable accuracy under stronger noise | ✅ right target, and currently unmet on every clause |

### 2.2 What needs sharpening

1. **Pick the right memory comparator.** The table's 47 % is versus FP32
   Adam. 8-bit Adam is ~10 B/param (4 w + 4 g + 2 moments), so packed
   4-bit GDMC (8.5) is only **~15 % smaller**, before per-block scale
   metadata. If the momentum is also 8-bit, 6.5 vs 10 = 35 %, but then it
   is a *different algorithm* (quantized-momentum GDMC) that no one has
   shown is stable. The honest headline is "roughly on par with, or
   modestly better than, 8-bit Adam", and it must be measured end-to-end
   (activations, temporary buffers, peak RSS/nvidia-smi), not per-parameter
   arithmetic.
2. **"Discrete proposals depend less on gradient magnitude" is only true
   for the sign variant.** The project's current best method, v3
   (`k_i ∝ |g_i|/g_ref/δ`), is explicitly magnitude-dependent; it trades
   scale-invariance for the fine-grid fix. Any noise experiment must state
   *which* GDMC variant it is testing (v1 sign, v2 sign(momentum), or v3
   magnitude-scaled) — they have different invariance properties.
3. **Acceptance power, not just acceptance placement.** A separate clean
   batch removes the optimism bias, but D1 shows the deeper issue: with a
   1 % move-set and one grid step, ΔL is below minibatch noise, so
   acceptance is ~1 regardless. The ablation should measure the *ΔL
   signal-to-noise ratio* and the accepted-step-size
   (`accept_rate × k × δ`), and include a β/ΔL sensitivity sweep. Without
   that, "acceptance filters harmful proposals" is not falsifiable on this
   pipeline.
4. **Reconcile the two stories.** The feedback's thesis is
   *noise tolerance*; the project's most robust empirical finding is
   *momentum at coarse grids* (and momentum *hurts* at 2 bits on
   Fashion-MNIST). Those are compatible only if momentum is framed as the
   denoiser and sign-proposals as the magnitude-error fix. The ablation
   matrix (accept vs always-accept × momentum on/off × bits) is the right
   way to settle it, and it is missing from the current design.
5. **The "realistic noise" experiment needs a batch-size arm, and the
   repo has none.** Every experiment uses a fixed batch size (128 for
   MNIST/CIFAR, 32 for toy); the `b2/b4/...` tokens in curve filenames are
   *bits*, not batch. A small-batch arm is the cheapest way to make both
   the proposal *and* the acceptance evaluation noisy, and it is new work.

### 2.3 Already known internally

The feedback lands close to `docs/future_work.md`, which already contains:
L2 (momentum / "discrete Adam"), L6 + Fix 6.1 (held-out Metropolis batch),
L11 (snap-on-the-fly / memory), L10 (SG-MCMC baseline), and the explicit
"what this won't fix" section. What is *new* in the feedback and genuinely
missing from the repo is: (i) gradient-noise injection as the primary
independent variable, (ii) the memory *accounting* and packed-weights
implementation, (iii) confidence intervals / degradation-from-baseline
reporting, and (iv) 8-bit Adam / ECO-style low-bit optimizer baselines.

### 2.4 Where the feedback could mislead if followed literally

* It proposes to start with GDMC at 4/8 bits vs FP32 Adam. As the project
  stands, that comparison is contaminated by D2/D3 (under-tuned Adam and
  QAT). Fixing the baselines has to come **first**, otherwise a flat
  noise-resilience curve will be uninterpretable.
* "Evaluate acceptance on a separate training batch" is necessary but not
  sufficient (see 2.2.3): the extra forward pass costs ~2× step time and
  will still be inert at 1 % move-set / 1 grid step.
* It assumes 4-bit packed weights with FP32 gradients is representable
  today; the repo cannot even run at that memory profile, so the memory
  experiment is a from-scratch engineering task (persistent packed
  weights, no master copy, bounded rollback), not a measurement.

### 2.5 Verdict

**Accept the feedback as the right research direction, with three
amendments: (1) baseline repair is a prerequisite, not a parallel task;
(2) the memory claim must be re-based on 8-bit Adam and measured as peak
end-to-end memory; (3) its headline noise-resilience hypothesis is not
supported by the first direct test (§3.3), so the study should be framed
as an open question — and the acceptance-vs-always-accept ablation should
be treated as a primary result, not a control.** Everything else in the
feedback is either correct or already an internal TODO.

### 3.3 Gradient-noise study (probe 2, reproduced as experiments/14)

**Setup.** MNIST MLP `784-256-256-10`, full 60 K train, batch 128,
8 epochs, 3 seeds (0/1/2); **fixed initialization per seed** (state_dict
reused across every cell); `shuffle=False` so minibatch order is identical
across methods; noise `ε = ρ · RMS(g) · N(0,1)` per tensor added to the
**proposal gradient only** (the Metropolis loss is a clean forward pass);
ρ ∈ {0, 0.1, 0.3, 1, 3}. Methods: FP32 Adam (`lr=1e-3`), GDMC v2 at 4 and
8 bits (`β1=0.9, k=1, move_frac=0.01, β=2.0`), and GDMC-8 with `β=0`
(identical proposals, always accept).

The prototype pilot (`results/review/noise_pilot.csv`, 60 runs) has been
re-run with the fixed optimizer and expanded into
[`experiments/14_noise_study.py`](../experiments/14_noise_study.py): 66 runs
using the built-in noise hook, an accept-vs-always-accept ablation at *every*
noise level, and a separate-acceptance cell. The table below is from that run
(`results/raw/noise_study.csv`).

**Best test accuracy (mean, n=3) and degradation from each method's own
noise-free result:**

| method | ρ=0 | ρ=0.1 | ρ=0.3 | ρ=1 | ρ=3 | Δ(ρ=3 − ρ=0) |
|---|---:|---:|---:|---:|---:|---:|
| FP32 Adam | 0.9793 | 0.9781 | 0.9788 | 0.9782 | **0.9746** | **−0.0048** |
| GDMC-8, Metropolis on | 0.9733 | 0.9741 | 0.9728 | 0.9687 | 0.9490 | −0.0243 |
| GDMC-8, always accept | 0.9733 | 0.9741 | 0.9728 | 0.9687 | 0.9490 | −0.0243 |
| GDMC-4 | 0.9260 | 0.9285 | 0.9285 | 0.9146 | 0.8942 | −0.0318 |
| GDMC-8, separate acceptance | — | — | — | 0.9613 | 0.9396 | — |

**Findings.**

1. **Adam is the more noise-robust optimizer here, not GDMC.** Adam loses
   0.48 points at ρ=3; GDMC-8 loses 2.43 and GDMC-4 loses 3.18 — a 5–7×
   larger degradation. At ρ=3 every GDMC variant is significantly below
   Adam (Welch p ≤ 1e-4). The noise does not overturn the ranking; it
   widens the existing gap (ρ=0 gap 0.6 pt → ρ=3 gap 2.6 pt).
2. **The acceptance step contributes nothing, with or without noise.**
   GDMC-8 with Metropolis vs always-accept is identical to four decimal
   places at *every* noise level (p = 1.0), and the reported acceptance
   fraction stays 1.000 even at ρ=3. With a 1 % move-set and one grid step,
   ΔL is below minibatch noise regardless of how noisy the gradient is, so
   the Metropolis test has no signal to act on. This is the mechanism
   ablation the feedback asks for, and it comes out negative. A *separate*
   acceptance batch is slightly worse (0.9396 vs 0.9490 at ρ=3, acceptance
   rate 0.998 vs 1.000), so the same-batch optimism bias was not the problem.
3. **Therefore "GDMC tolerates stronger gradient noise than FP32 Adam" is
   not supported by this pilot.** The data supports the project's earlier
   framing instead: at 8 bits, GDMC v2 behaves like grid-projected
   momentum sign-SGD, and Adam remains ahead.

**Caveats (this is a pilot, not a powered result).** One task and
architecture, 8 epochs, 3 seeds, Gaussian noise only (no outlier or
sign-flip injection), no batch-size or gradient-quantization arm. GDMC is
quantized while Adam is not, so part of the *level* gap is the constraint
rather than noise — the *degradation* column is the noise-specific part.
The 8-bit-Adam baseline now exists (see
[fixes_2026-10-04.md](fixes_2026-10-04.md)); replicating on a second task
and with outlier noise remains open.

## 4. Recommended order of work

1. **Repair the baselines** (blocking):
   * Adam lr sweep at each long-run config (`1e-3 vs 3e-3 vs 1e-2`), report
     the best per task with CIs.
   * Projected-GD with `lr` set relative to δ (e.g. `lr ∈ {0.25δ, 0.5δ, δ}`).
   * Add two low-bit baselines: 8-bit Adam, and momentum-signSGD (i.e. GDMC
     with acceptance forced on) to isolate the contribution of the
     acceptance step.
2. **Make acceptance observable**: separate `B_grad`/`B_accept`, log
   `E[ΔL]`, `sd[ΔL]`, acceptance fraction, and accepted step size; delete
   or implement `accept_on`.
3. **Add the noise hook** (5 lines, as in probe 2) and run the
   noise-resilience curve on one fixed task with CIs (n ≥ 5) seeds and
   the mechanism ablation (accept/no-accept × momentum/no-momentum ×
   4/8-bit). Test Gaussian then outliers then sign flips.
4. **Then memory**: persistent packed weights, bounded proposals/rollback,
   lazy move-set selection (`rand < frac` instead of `randperm`), and
   measured peak memory vs 8-bit Adam.
5. **Then scale** to the modest Transformer; fix the aggregator to key on
   the full config; add a smoke test + CI that asserts the proposal changes
   the weights at every bit-width.
